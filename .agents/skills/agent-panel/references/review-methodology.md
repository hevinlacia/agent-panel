# 深度审查方法论（agent-panel-code-review）

> 本文件是四轮审查法的完整执行标准。目标：把“看过 diff”升级为“验证过行为”。审查的产出不是“看了什么”，而是“排除了什么、剩下了什么”。

## 0. 总原则

1. **diff 是线索，不是证据**。diff 只告诉你改了哪几行；问题几乎总在 diff 之外的交互里（调用方、被调方、并发方、数据现状）。
2. **先理解意图，再读实现**。没读 technical-plan 之前不下任何结论；实现与方案不符是最高优先级 finding。
3. **每个“没问题”都要有证据**。“检查过 X，方式是 Y，所以 Z”才算结论；“应该没问题”不算。
4. **宁可 BLOCKED 不可漏报**。漏掉的严重问题会流到生产；误报的改进建议只浪费几分钟。
5. **门禁发现问题 = 全面复审信号**。gate 非 passed 时由主 agent 结合会话上下文亲自重过四轮审查法，重点回答“为什么之前没发现”，不是只修 gate 指出的那几处。
6. **全量审查 = diff + 全部必要上下文代码**。非增量审查不只看 diff hunk：改动文件的完整实现、调用链、Mapper XML、枚举、配置都在审查范围内；扩大阅读清单写进审查概览，是审查深度的直接证据。

## 1. Pass A — 变更盘点

从材料 JSON 的 `repos[].files` 建变更清单，给每个文件打标：

- **改动类型**：新增逻辑 / 修改既有逻辑 / 删除逻辑 / 移动重构 / 纯配置。
- **风险面**：涉及写库？涉及 redis？涉及 MQ 收发？涉及事务？涉及状态流转？涉及金额/库存数量？涉及对外契约（API/MQ payload）？
- **共享度**：改动资产是单消费方还是多消费方共用（SQL statement / Service 方法 / DTO 字段 / 常量枚举 / 配置 key / MQ topic）。多消费方共用 = 高风险项，Pass B 必须按 §3-C11 枚举全部消费方。
- **风险标签核对**：材料 `riskTags` / `inventoryRisk` 是否覆盖了你看到的高风险文件；漏标的在结论里补上。

产出：3-5 个最高风险文件（优先：核心状态机、库存数量、MQ 消费、批量写库、事务边界），Pass B 按此优先级深读。

**常见漏判**：只看 additions 大的文件。删除/小改动文件（尤其 `if` 条件微调、注解增删、参数默认值变化）经常是行为翻转点。

## 2. Pass B — 逐文件深读 + 扩大阅读

对每个高风险文件：

1. **读完整上下文**：改动函数所在的完整类/方法体，而不是只有 hunk。确认改动行所处的分支、循环、事务边界。
2. **调用方核对**：`rg "<方法名>("` 找所有调用点，逐一确认参数、返回值、异常处理是否仍然成立。改签名/改语义时，漏改的调用方是最常见 bug。
3. **被调方核对**：新调用的下游（Service/Mapper/HTTP client）是否真的支持传入的参数组合；返回值可能为 null/空集合吗。
4. **数据契约核对**：改了实体/Mapper/DTO → 读对应 Mapper XML 全文，确认列名、resultMap、where 条件、索引匹配；WMS 表字段驼峰/下划线混用，凭其他表的风格猜列名必错。
5. **枚举与常量核对**：新状态值/类型值是否在后端枚举里注册；前端/PDA 是否仍传旧值；字典表/文案映射是否要同步。
6. **共用资产核对（多消费方共用时必做）**：改动落在共用 SQL/方法/DTO/常量/配置上时，按 §3-C11 枚举全部消费方（仓内 + 跨仓 + 前端/PDA），逐一确认旧语义未被破坏，并评估是否能用更收敛的改法（新增分支/新增字段，而不是改既有默认分支/既有字段含义）。**改语义远比加字段危险**：同一参数/字段含义从 A 变 B 时，必须逐个消费方确认。

扩大阅读以“能准确判断问题”为度，不通读仓库；每读一个关键文件记入结论的「扩大阅读」清单。

## 3. Pass C — 横切检查清单（逐项必须给结论）

每项格式：`结论（pass/fail/na）+ 查了什么 + 证据（文件:行 + 引用）`。na 必须说明为什么本需求不涉及。

### C1 空值与边界
- 新增/修改的参数、DB 字段、Map 值、集合元素：null 时走哪条路径？空集合时循环/流操作返回什么？
- 拆分/截取/下标/强制转换：越界、负数、超长输入。
- 典型 bug：`list.get(0)`、`map.get(x).getY()`、`Integer` 拆箱 NPE、`String.split` 空串。

### C2 并发与事务
- 写操作是否在事务里？事务边界是否包住了该原子化的多步写？`@Transactional` 失效场景（同类内部调用、非 public、异常被吞）。
- 事务内禁止：MQ 发送、HTTP 调用、redis 长操作（拉长事务、回滚不一致）。
- 检查-then-act 竞态：先查库存再扣减、先判状态再更新——有没有锁/版本号/条件更新兜底。
- 典型 bug：事务里发 MQ，回滚后消息已出去；并发下两个请求同时通过状态检查。

### C3 幂等与重试
- MQ 消费：重复投递会怎样？消费前查单据状态/唯一键防重吗？
- 接口：前端重复提交、网关重试会怎样？
- 定时任务：上一次没跑完又触发、同一单被扫两次会怎样？
- 典型 bug：MQ retry 直接 +qty 两次；job 半途失败重跑造成重复单。

### C4 状态机合法性
- 每个状态变更：从哪些状态允许流转到目标状态？非法当前状态时是拒绝还是静默通过？
- 中间态：更新多张表/多个字段时，失败一半是什么状态？有补偿吗？
- 典型 bug：`update ... set status=X` 不带 `and status in (...)` 前置条件，并发下把已取消单又改成进行中。

### C5 SQL 与性能（红线：接口平均 3 秒内、无慢 SQL；OOM 同为阻断级）
- 新增/修改 SQL 逐条过：where 条件走索引吗（EXPLAIN 佐证或明确说明依据）？大表更新有 where 吗？
- 循环内查库/更新（N+1）：批量化或明确说明数据量可控的理由。
- 大结果集：一次性 `selectList` 无分页/无 limit？深分页 offset？
- 事务里做重计算/外部调用拖长锁持有时间。
- 内存与批量边界（OOM 红旗模式，逐个扫，命中即至少 P1）：一次性 `list()`/`selectList` 全量进内存后做 group/filter/导出——量级谁保证有界？单头-明细联合处理无二次分批（明细倾斜让外层分页失效，见 `exp-wms-export-detail-oom`）；Excel/文件生成全量加载；static/ThreadLocal 集合无界累积；MQ 批量消费、线程池队列、pageSize 无上限保护。
- 量级证据要求：C5 结论为 pass 时必须写出本次改动的量级假设（单次处理 N 条、目标表规模 M 万、峰值 QPS 估计）；没有数字的“性能无问题”是无效结论。
- 典型 bug：新增 where 条件字段没索引；`in` 子查询改成 join 后行数爆炸；定时任务全表扫；单头导出联查明细一次拉 10 万条 OOM。

### C6 跨仓契约一致性
- 多仓需求：A 仓新字段/新枚举值，B 仓消费方是否同步改了？MQ payload/DTO/接口出入参逐字段对。
- 状态码/代号 vs 文案：状态流转字段必须用代号（数字/编码），文案只做展示；发现互传文案的契约是 finding。
- 典型 bug：生产者加了字段消费者没读（漏功能）或改了枚举值消费者未同步（静默错分支）。

### C7 配置与上线顺序
- 新增 Apollo/Nacos 配置项：有默认值吗？开关关闭时走老逻辑吗（可回退）？
- release-manifest 核对：DDL、配置、Topic/Group、Job、人工动作与代码一致；代码先上但配置没配 = 上线即故障。
- 典型 bug：新逻辑读的 Apollo key 拼错/没在配置中心建；DDL 没进 release-manifest。

### C8 库存账本（命中库存风险时必做，详见 §4）
- DB 库存与 redis 可用量双账本必须同时评估，缺一不可。

### C9 日志与可观测
- 关键分支（状态变更、数量变更、外部调用、异常捕获）有符合 WMS 规范的日志吗（tid 链路、关键单号、前后值）？
- 异常被 catch 后静默吞掉（只打 log 不处理/不抛）是 finding。
- 典型 bug：catch (Exception e) { } 或只打 e.getMessage() 丢栈。

### C10 安全与数据暴露
- 新接口：权限注解/登录校验齐吗？入参有没有直接拼 SQL/脱敏缺失？
- 日志/异常信息里是否带手机号、地址等敏感明文。

### C11 共用资产影响面收敛（改动命中多消费方共用资产时必做）

先打共享度标签：**单消费方**（只有本需求模块调用）→ 记录证据即可判 pass；**多消费方共用**（同一 Mapper statement / Service 方法 / DTO 字段 / 常量枚举 / 配置 key / MQ topic 被其它模块、其它应用或前端/PDA 复用）→ 必须走完下面四步。

1. **枚举全部消费方（不许抽样、不许“应该不影响”）**
   - 仓内：`rg -n "<statement-id>|<方法名>|<字段名>|<config-key>" <repo>`，逐个确认调用层（Controller / Biz / Service / Job / MQ consumer）。
   - 跨仓：全工作区 `rg --no-ignore`。**工作区 `.gitignore` 默认屏蔽子仓，不加 `--no-ignore` 会静默漏检**（同一条命令漏检时会得到“只有本模块在用”的假结论）；同时搜前端/PDA（`.kt/.ts/.vue`）与其它后端应用的同名副本。
   - SQL：确认该 statement 是否被 `<sql>` / `<include>` 复用，是否有多个 Mapper 方法指向同一段 where；同名 statement 在别的仓库是否有独立副本（副本互不影响，但会同步埋同样的坑 → 记 P3 提示，不作为本次阻断）。
   - DTO/VO：字段改名/改含义时找全部读写方；前端/PDA 实体字段与后端 DTO 必须成对核对。
2. **逐一判定波及面**：对每个消费方回答「它的既有依赖是否被破坏」。**改语义（同一参数/字段含义从 A 变 B）远比加字段危险**——加字段多数向后兼容，改语义必须逐个确认。
3. **优先收敛改法**（降低耦合；最小 diff 不是唯一目标）
   - 新增 statement / 新增分支，而不是改既有 statement 的默认分支；
   - 新增参数并保持旧调用点行为 byte-identical（新分支只在显式传新值时生效）；
   - 新增 DTO 字段，而不是改既有字段含义；新增枚举值，而不是改旧值；
   - 新接口 / 新 topic，而不是改既有对外契约。
4. **结论落证（写进 code-review-ai.md 横切小节 + annotations）**：`改了哪个共用资产 → 消费方枚举 N 个（列路径）→ 各自影响判定 → 为什么只影响本需求模块 / 哪些模块受影响及其可接受性`。

定级：
- 旧调用点行为被**非本需求预期**地改变 → **P1**（语义漂移，回归范围不可控）。
- 波及其它模块既有功能（尤其拣货/库存/回单等主链路）→ **P0/P1**，按波及面定级。
- 共用资产消费方未枚举完就写「无影响」= 无效结论，审查不得 PASS（至少 P2）。
- 为省 diff 直接改共用 statement 默认分支 / 改字段既有含义，且未评估收敛改法 → **至少 P2**（耦合风险，即使当前测试通过）。
- 该资产确实单消费方、并用 `rg` 证据写清唯一调用链 → 判 pass，证据进「扩大阅读」。

### C12 影响范围计划 vs 实际改动核对（technical-plan.md 有影响范围清单时必做）

补 C11 的盲区：C11 从 diff 出发找消费方（防“改坏别人”），C12 从计划出发核对落地（防“漏改该改的”）。两个方向互补，缺一不可。

1. **正向（计划 → diff）**：清单中每个「需要同步修改」的关联模块/调用方/契约消费方，实际 diff 是否有对应改动？
   - 有 → 确认改动满足该模块的诉求（不是只改了个寂寞：改了枚举定义但消费方字典/文案映射没同步，也属漏改）。
   - 没有 → 查清单/notes.md 是否有不改依据；有依据判 na；无依据 = 漏改 finding（该模块消费本需求产出/有独立既有功能 → P1；纯防御性/展示性 → P2），并建议补改或退回开发确认。
2. **反向（diff → 计划）**：diff 覆盖的模块/文件哪些不在清单内？
   - 清单外改动 = 未声明的影响面：逐个判断是本需求合理延伸还是影响面扩散。扩散且未经评估 → 至少 P2，结合 C11 枚举消费方，并建议回写 technical-plan.md。
3. **结论落证**：核对结论（清单 N 项：落地 x / 不改有据 y / 漏改 z）写进 code-review-ai.md 横切小节 + review-checklist（id 如 `impact-plan-vs-diff`）；漏改/扩散项进对应 P 级小节 + annotations hunk note。

定级：
- 清单声明要改的模块漏改，且该模块消费本需求产出（契约/数据/事件）→ **P1**（功能断链，自测/UAT 只回归主链路时可能测不出来）。
- diff 波及清单外模块且无评估 → **至少 P2**。
- 清单缺失/为空（旧需求未维护清单）→ 写 na 并在审查概览说明，不虚构清单。

## 4. 库存账本评估矩阵（命中“库存”风险标签时必填，不能写“无”）

逐项回答，每项给代码证据：

1. **单据终态**：单据最终是活跃单还是死亡单（取消/拦截/删除）？
2. **DB 库存**：onHandQty / allocatedQty 各自怎么变？临时库位、回库单是否处理？
3. **redis 可用量**：建单 −qty、真取消 +qty、恢复 −qty、回退是否保持占用（**活跃单不释放，死亡单才释放**）。
4. **重复释放**：cancel + delete、intercept + cancel、MQ 重试、接口重试，有没有路径把同一占用释放两次？
5. **遗漏占用**：库存回池后是否继续分配/拣货但没有重新占用？
6. **幂等**：重复消费/重复调用会不会多次 ±qty（唯一键/状态前置条件/redis 原子操作）？
7. **验证证据**：DB 前后值、redis 前后值、日志、单测、边界状态，至少一类。
8. **结论**：账本是否平衡；不平衡必须 BLOCKED。

## 5. Pass D — 反向验证（构造反例推演）

对每个“看起来对”的关键分支，构造至少一个反例并推演代码实际行为：

- 入参反例：null、空串、空集合、0、负数、超长、非法枚举值。
- 状态反例：在异常当前状态下调用（已取消单再发货、已审单再改）。
- 时序反例：两请求并发、消息乱序、任务与人工操作交错。
- 重复反例：同请求打两遍、同消息消费两遍、job 连跑两轮。
- 数据反例：存量脏数据（老单据没有新字段）、边界数量（刚好 0、刚好库存上限）。

推演输出不是“应该没问题”，而是“输入 X 时代码走到 Y 行，结果是 Z（可接受/有问题）”。

## 6. Finding 质量标准（P0-P3 分级）

风险分级与判定（逐条核查、精准标记，区分真实问题与误报，不输出无意义冗余告警）：

- **P0 阻断**：线上故障、数据错乱、安全漏洞、库存账本不平衡——必须修复，禁止合并。
- **P1 严重**：性能问题（慢 SQL、超 3 秒接口、N+1）、潜在数据风险、并发缺陷、幂等缺失且有真实重试路径——必须修复。
- **P2 一般**：代码可读性、冗余问题、防御不足、可维护性——建议修复。
- **P3 优化**：可选重构，不阻断上线。

执行规则：

- 每条 finding：`[P0/P1/P2/P3]` `[逻辑/性能]` `文件:行` + 问题描述 + 触发条件 + 具体修复建议。
- **先验证再上报**：可疑告警先读完整实现/推演反例确认真实性再定级；算法式猜测直接进报告就是误报污染。验证不了的写 Open Question（附所需材料），不占 P 级，也不静默丢弃。
- **不凑数**：风格偏好、无实际影响的告警不输出；同一问题不跨小节重复罗列。
- **P0 非空 → `Review Gate: BLOCKED`**；P1 非空 → 放行但门禁展示 ⚠ 警示（提醒用户 P1 待修复）；门禁按文档实际内容校验，结论与内容不一致时以内容为准。
- **双写一致性**：每条 P0-P3 finding 必须同时出现在两处——详细审查文档（code-review-ai.md 对应 P 级小节）和 annotations 的 hunk note（锚定所在 hunk），保证差异页右侧备注与文档结论一一对应；只写一处视为产物不完整。

## 7. 自测清单交叉评估（必做）

test.md 的自测清单分三类（主流程 / 边界场景测试 / 高并发·大流量场景测试），其中边界与并发流量类含「风险场景分析」+ 测试清单。审查必须与它交叉核对，并产出独立小节「## 自测清单交叉评估」（门禁强制非空）：

1. **风险覆盖度**：diff 与扩大阅读发现的边界/并发流量风险，自测的风险场景分析是否覆盖？遗漏的逐条列出，建议补自测（P2）。
2. **结果印证**：自测「失败 / 无法测试」的项与审查发现互相印证——失败场景对应代码重点核查；无法测试的原因（如环境未部署）与风险等级一起评估。
3. **矛盾检测**：自测声称通过、但代码里该场景没有真实保护（无幂等键、无锁、无条件更新、无判空）→ 直接 P1，并在 annotations 加 hunk note。
4. **保护确认**：自测风险分析里列出的并发/重复场景，逐条确认代码里有对应防护（幂等/锁/状态前置条件/redis 原子操作），确认结果写进交叉评估。

## 8. 常见漏判模式（自检）

浅审查的典型痕迹，出现任何一条说明审查深度不够：

- 结论里全是“符合预期”“无问题”但没有引用任何文件行号。
- 只评价了新增代码，没核对被修改逻辑的既有调用方。
- 横切清单每项都是 na，但材料里有 MQ/事务/批量写库。
- 没有做任何扩大阅读（结论概览的扩大阅读清单为空）。
- 严重问题数量与风险标签数量明显不匹配（5 个库存文件 0 个库存 finding 且无账本评估）。
- 改了多模块共用的 SQL / Service / DTO / 配置，结论里只核对了自己模块的调用方，没有枚举全部消费方（尤其跨仓与前端/PDA），或只写“其他调用方不受影响”而不给消费方清单与证据。
- 为了最小 diff 直接改共用 statement 的默认分支、或改 DTO 字段既有含义，没有评估「新增分支 / 新增字段」的收敛改法。
- 跨仓检索没加 `--no-ignore`，因工作区 `.gitignore` 屏蔽子仓而漏掉同名副本与跨仓消费方，得出“只有本模块在用”的假结论。
- 只做了 C11（diff → 消费方）没做 C12（计划 → diff）：technical-plan.md 影响范围清单里声明要同步修改的模块，实际 diff 里没改，审查结论里却没提；或 diff 改了清单外的模块却没评估是否影响面扩散。
- 未变更文件的问题引用直接来自工作区读取，没有 `git show targetCommit:path` 交叉取证——本地工作区落后远端时（如 master 落后 2 个 commit），未变更文件（如 listener）全是旧版，会把已修复的旧代码判成 P0（WMS-134 实证误报）；无 bash 的 reviewer 尤其要靠主 agent 预取材料或 handoffHints 声明。
